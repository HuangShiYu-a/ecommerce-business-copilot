## 1. 项目定位与范围

### 1.1 项目名称

- 英文：**E-commerce Business Copilot**
- 中文：**电商智能客服与运营决策 Copilot**

### 1.2 核心定位

面向电商平台 / 商家**内部**客服与运营人员，提供商品、订单、履约、售后、库存、销售与运营决策相关的智能辅助能力。

一句话：

> 客服侧负责商品 / 订单 / 履约 / 售后问题的查询、判断与回复辅助；运营侧负责销售、商品、库存、价格、促销及商品健康度分析，并按业务规则生成运营建议；Agent 通过业务能力查询**当前业务数据**、通过知识检索获取业务规则、通过工作流编排多步骤任务，并对高风险操作引入人工审批与可追溯记录。

### 1.3 服务对象与交互主体

| 维度 | 说明 |
|------|------|
| 使用者 | 真人客服、运营人员（内部员工） |
| 交互方式 | 内部工作台 / Chat：员工向 Agent 提问或发起任务 |
| 最终消费者 | **不直接**与本系统对话（V1） |
| 客服工作流 | 消费者 ↔ 真人客服 ↔ Agent（旁路 Copilot） |

### 1.4 产品形态

```text
Ecommerce Business Agent
            │
  ReAct Tool-Orchestrator（LLM 看工具目录自主编排 → 确定性工具裁定）
            │
   Workspace Mode（能力档案：UNSET / 客服 / 运营，切换需用户确认）
            │
   ┌────────┴────────┐
   ↓                 ↓
Customer Service   Operations
（客服能力集合）    （运营能力集合）
```

两边共享：商品、订单、库存、客户、售后、反馈、知识、分析等公共域。  
**不是**两个完全独立的程序，而是一个 Agent（ReAct 工具调用式）+ Workspace Mode 能力档案 + 分角色工具目录。

### 1.5 明确不做（V1）

| 项 | 原因 |
|----|------|
| C 端消费者 AI 客服 | 范围膨胀；与「企业内部 Copilot」定位不符 |
| 独立「销售」角色 | 销售分析纳入运营 |
| 独立「管理员」角色 | 不做完整 Admin 后台；审批与审计以业务原则约束（见第 2.4、2.5 节），权限模型留给后续设计 |
| 批量下架 / 大规模自动改价 / 自动退款落地 | 高风险执行非 V1 重点；以建议 + 人工审批为主 |
| 完整数据仓库（ODS/DWD/DWS/ADS） | V1 用业务库联机查询 + 能力层动态计算即可；非流式实时数仓 |
| 流式实时架构（Kafka 等） | 「当前业务数据」指查询业务库当下状态，非事件流实时特征 |

可选预留（非 V1）：消费者 → Customer-facing AI → 客服 Agent / Human。

### 1.6 业务规则前提

平台规则（淘宝 / 京东 / 拼多多等）仅作**模拟业务规则参考**，因平台、类目、商家类型与时间而异。项目中规则必须**可配置**，并分层：

| 层级 | 含义 | 示例 |
|------|------|------|
| Legal | 法定 / 监管底线 | 七日无理由退货基本要求 |
| Platform | 平台规则（可抽象为 `default`，后续扩展） | 平台售后细则 |
| Store | 本店业务规则 | 最低毛利、安全库存、健康分阈值、审批阈值 |

阈值与评分标准属于 **Store 规则**，不得表述为「行业统一真理」。

### 1.7 事实 / 规则 / 智能分工（业务层）

| 层 | 负责回答 | 说明 |
|----|----------|------|
| 结构化业务数据 | 「现在发生了什么？」 | 库存、订单状态、销量等业务事实；**具体库产品由 Database Design 决定** |
| 业务知识 | 「按规则应该怎么处理？」 | 售后/客服/库存/运营等规则与规范；检索实现由 Knowledge/RAG Design 决定 |
| 确定性计算与判断 | 「算出来是什么 / 是否符合规则？」 | 指标、资格等须基于结构化事实与明确规则，不得由模型臆造 |
| LLM | 「如何理解、综合、解释、生成？」 | 理解问题、组织上下文、解释结论、生成建议与回复草稿 |
| 工作流编排 | 「多步骤任务如何推进？」 | 步骤顺序、分支、循环与人工审批节点；具体框架由 Workflow Design 决定 |

### 1.8 业务级原则（必须遵守）

**原则 1：事实与判断分离**  
结构化数据提供事实；业务规则提供约束；确定性计算给出数值与资格结论；LLM 负责理解、综合、解释与生成。

**原则 2：Agent 不得臆造**  
事实不存在、数据不可用、规则冲突或能力不可用时，不得猜测结论（详见 2.6）。

**原则 3：高风险操作必须人工确认**  
建议 → 人工审批（业务流程节点）→ 执行（详见 2.4、3.2）。

**原则 4：高风险操作必须可追溯**  
改变业务状态的操作须保留操作与审批记录（详见 2.5）。

**原则 5：数据访问最小必要**  
Agent 仅在员工业务权限范围内取数，敏感信息最小必要展示（详见 2.7）。

> AI 使用约束（业务表述）：关键业务判断必须基于结构化事实和明确规则；模型不得自行臆造业务事实或计算结果。具体采用规则服务、领域服务、SQL 或其他实现，由 Technical Design 决定。

## 2. 角色定义

### 2.1 角色 A：客服 Copilot

| 项 | 内容 |
|----|------|
| 定位 | 服务**真人客服**，不替代客服与消费者沟通 |
| 核心目标 | 提高信息获取、问题判断与回复生成效率 |
| 主要工作 | 售前咨询、售中跟进、售后处理、客户反馈、复杂问题升级 |
| 典型产出 | 事实摘要、资格判断依据、处理建议、**可发送的回复草稿** |
| 边界 | 查询 / 分析 / 建议可自动；改变业务状态（退货申请、退款等）需人工确认 |

### 2.2 角色 B：运营 Copilot

| 项 | 内容 |
|----|------|
| 定位 | 直接服务**电商运营人员** |
| 核心目标 | 监控经营、识别异常、分析原因、给出可执行建议 |
| 主要工作 | 销售 / 商品 / 库存 / 价格 / 促销分析、商品健康度、补货与生命周期建议 |
| 典型产出 | 指标摘要、异常诊断、风险等级、运营建议、经营报告 |
| 边界 | 建议自动生成；改价、建活动、补货执行、下架等需人工确认 |

### 2.3 两角色工作方式对比

```text
客服：当前个案问题 → 查事实 → 查规则 → 判断 → 建议/草稿 → 人确认 → 回复消费者

运营：业务问题 → 取数 → 算指标 → 识别异常 → 分析原因 → 建议 → 人确认 → 执行
```

### 2.4 操作人与审批人（业务概念，非第三角色）

「人工审批」是**业务流程节点**，不是一句空泛的「需要人确认」，也不为此新增独立「管理员」角色。

| 概念 | 含义 |
|------|------|
| 操作人 | 向 Agent 发起任务、接收建议的工作人员（客服或运营） |
| 审批人 | 对高风险执行做出批准/拒绝的人员 |

约定：

- 审批人可以与操作人是**同一人**（例如客服确认自己发起的售后执行）。
- 也可以是具有更高权限的其他工作人员（具体权限矩阵留给后续权限设计，本文不展开）。
- 典型链路：`Agent 建议 → 审批人确认 → 执行动作 → 记录结果`。

示例：

- CS-09：Agent 提出售后处理方案 → **客服（审批人）确认** → 执行。
- OP-09：Agent 提出调价建议 → **人工确认** → 方可执行改价。

### 2.5 高风险操作可追溯（审计约束）

所有**改变业务状态**的高风险操作，应保留操作与审批记录，至少覆盖：

| 记录项 | 说明 |
|--------|------|
| 谁提出 / 谁批准 | 操作人、审批人 |
| 什么时间 | 建议时间、审批时间、执行时间 |
| 批准了什么 | 动作类型、对象、关键参数（如退款金额） |
| 执行结果 | 成功 / 失败及结果标识 |

闭环：`Agent 建议 → Human Approval → Action Result → 可追溯记录`。

> 本文只定业务原则；是否独立审计表、字段形态由 Database / Technical Design 决定。不等于现在做 Admin 系统。

### 2.6 信息不足 / 数据缺失 / 规则冲突时的处理

信息不足、数据缺失、规则冲突或系统能力不可用时，Agent **不得臆测结论**，应：

1. 明确说明缺失项或冲突点；  
2. 请求补充信息；或  
3. 降级处理（仅基于已有可靠事实作有限说明）；或  
4. 转人工。

示例：客户问「能不能退？」但未提供订单号/商品/购买时间 → 请求补充，不得猜测可退。  
库存数据不可用 → 明确告知无法确认，不得声称「有货」。

### 2.7 数据访问边界（业务级约束）

Agent 只能访问**当前员工业务权限范围内**的数据；涉及客户敏感信息（如手机号、地址）时遵循**最小必要展示**原则。

| 约束 | 说明 |
|------|------|
| 范围 | 如当前店铺 / 授权业务范围（具体模型留给权限设计） |
| 敏感字段 | 完整手机号、详细地址等按最小必要展示或脱敏 |
| 禁止 | 越过员工权限的「任意客户全量透视」 |

后续 Tool 设计应自然形成：`当前用户上下文 → 权限过滤 → 再取数`，而非无约束地按 ID 取全量敏感信息。V1 可用模拟权限上下文体现该原则，无需先做完整权限后台。

## 3. 业务能力域总览

系统暂分 **8 个公共 / 业务能力域**：

| 编号 | 能力域 | 客服重点 | 运营重点 |
|------|--------|:--------:|:--------:|
| 1 | 商品中心 | ✅ | ✅ |
| 2 | 订单与履约 | ✅ | △ |
| 3 | 售后服务 | ✅ | △ |
| 4 | 客户与反馈 | ✅ | ✅ |
| 5 | 销售分析 | △ | ✅ |
| 6 | 库存分析 | △ | ✅ |
| 7 | 价格与促销 | △ | ✅ |
| 8 | 商品健康与生命周期 | △ | ✅ |

`△` = 有条件使用，非主责。

### 3.1 Agent 能力抽象

| Agent 能力 | 客服 | 运营 |
|------------|:----:|:----:|
| 信息查询 | ✅ | ✅ |
| 数据统计 | 少量 | ✅ |
| 数据分析 | 少量 | ✅ |
| 规则检索 | ✅ | ✅ |
| 多步任务 | ✅ | ✅ |
| 推荐 / 决策支持 | ✅ | ✅ |
| 内容生成（回复草稿、报告） | ✅ | ✅ |
| 执行动作 | ✅（审批后） | ✅（审批后） |
| Human-in-the-loop | ✅ | ✅ |

### 3.2 风险与审批原则（业务层）

| 风险 | 典型行为 | 策略 |
|------|----------|------|
| 低 | 查询、统计、分析、检索、生成建议/草稿 | 可自动 |
| 中 | 资格判断、补偿建议、补货/价格/促销建议 | 可自动判断或生成；**执行**需审批人确认 |
| 高 / 关键 | 退款、实际改价、改库存、批量促销、批量下架 | **必须经审批人确认**，且须可追溯（见 2.4、2.5） |

## 4. 场景文档约定

### 4.1 场景 ID

- 客服：`CS-01` … `CS-12`
- 运营：`OP-01` … `OP-14`

### 4.2 统一字段模板

每个场景包含：

1. 场景名称 / 角色 / 优先级  
2. 典型问题  
3. 业务目标  
4. Agent 步骤  
5. 所需业务事实  
6. 所需业务规则（知识检索，实现方式不在本文锁定）  
7. 所需能力（业务能力，非最终函数名）  
8. 输出形态  
9. 风险与人工审批（含审批节点说明）  
10. 依赖与前置条件  

所有场景默认遵守第 1.8、2.4～2.7 节原则（尤其信息不足不得臆测）。

### 4.3 优先级定义

| 级别 | 含义 |
|------|------|
| **P0** | V1 **必须**实现，构成核心可演示闭环 |
| **P1** | V1 强烈建议；时间允许则实现 |
| **P2** | 后续扩展，不影响核心项目完成 |

> 实施提示（非改写 P0 清单）：落地时可在 Roadmap 中再拆 `P0-Core` / `P0-Extended`，避免 12 个 P0 场景平均用力；**本文业务层仍保留完整 P0 列表作为范围合同。**

## 5. 客服业务场景矩阵

### CS-01 商品基础咨询

| 字段 | 内容 |
|------|------|
| 角色 | 客服 |
| 优先级 | **P0** |
| 典型问题 | 「这个商品是什么配置？」「两款规格有什么区别？」「面料/材质是什么？」 |
| 业务目标 | 快速给出准确商品信息，并生成可发送回复草稿 |
| Agent 步骤 | 识别商品 → 查商品基础信息 → 查规格/变体 → 必要时查商品说明知识 → 生成回复草稿 |
| 所需业务事实 | 商品、SKU/规格、品牌、属性、价格、商品状态 |
| 所需业务规则 | 可选：商品 FAQ、使用说明、商品政策 |
| 所需能力 | 检索商品；获取商品详情；获取规格/变体 |
| 输出 | 准确商品信息 + 客服回复草稿 |
| 风险与审批 | 低；无需审批 |
| 依赖 | 商品主数据可用 |

### CS-03 商品价格与促销咨询

| 字段 | 内容 |
|------|------|
| 角色 | 客服 |
| 优先级 | **P1** |
| 典型问题 | 「现在多少钱？」「某活动能不能用？」「为什么页面价和后台不一致？」 |
| 业务目标 | 说明原价、现价、可用优惠与适用条件 |

| 输出 | 原价 / 现价 / 可用优惠 / 预计成交价 / 适用条件 |
| 风险与审批 | 查询：否；**实际改价必须审批**（本场景以查询为主） |
| 依赖 | 价格与促销数据；P1 可简化活动模型 |

### CS-04 商品推荐 / 替代商品

| 字段 | 内容 |
|------|------|
| 角色 | 客服 |
| 优先级 | **P1** |

| 所需能力 | 多条件检索商品；查询库存；商品对比/排序 |
| 输出 | Top N 推荐 + 价格/库存 + 推荐理由 |
| 风险与审批 | 低；无需审批 |
| 依赖 | 商品与库存可检索 |

## 6. 运营业务场景矩阵

运营与客服的区别：客服处理「当前个案」；运营处理「业务整体发生了什么、接下来做什么」。

### OP-01 销售经营概览

| 字段 | 内容 |
|------|------|
| 角色 | 运营 |
| 优先级 | **P0** |
| 典型问题 | 「这个月销售怎么样？」「过去 30 天 GMV 怎么变化？」 |
| 业务目标 | 给出周期内核心经营指标与对比摘要 |
| Agent 步骤 | 解析时间范围 → 查销售数据 → 统计 GMV/订单/销量/AOV → 与历史周期比较 → 生成摘要 |
| 所需业务事实 | 订单、订单明细、商品、客户（可选） |
| 所需业务规则 | 否 |
| 所需能力 | 查询销售指标；周期对比 |
| 输出 | 销售额、订单数、销量、AOV、同比/环比、主要涨跌商品 |
| 风险与审批 | 低；无需审批 |
| 依赖 | 订单时间与金额字段完整 |

### OP-04 库存风险分析（缺货）

| 字段 | 内容 |
|------|------|

| 业务目标 | 基于当前库存与历史销量估计消耗，识别缺货风险 |
| Agent 步骤 | 查当前库存 → 查历史销量 → 估计日均销/消耗 → 结合安全库存/补货周期 → 判风险 |

| 所需业务规则 | 可选：库存政策、安全库存、采购周期 |
| 所需能力 | 查询库存；查询销售；计算库存天数；计算缺货风险 |
| 输出 | 商品、当前库存、日均销、可维持天数、预计缺货日、风险等级 |
| 风险与审批 | 低；无需审批 |
| 依赖 | 缺货相关指标须基于结构化事实做确定性计算；模型仅解释，不得臆造库存或风险等级 |

### OP-05 补货建议

| 字段 | 内容 |
|------|------|

| 业务目标 | 基于历史销量趋势估计未来需求，结合库存政策给出补货建议（**非完整需求预测系统**） |

### OP-07 商品健康度分析

| 字段 | 内容 |
|------|------|
| 角色 | 运营 |
| 优先级 | **P0** |
| 典型问题 | 「帮我全面评估这个商品。」 |
| 业务目标 | 多维评分 + 问题诊断 + 运营建议（项目特色能力） |
| Agent 步骤 | 汇总可用维度事实 → 按 Store 规则加权评分 → 标注数据完整度 → 诊断 → 建议 |
| 所需业务事实 | **核心维度（建议必选）**：销售、库存、利润、退货、反馈；**可选维度**：评价、履约、流量/CTR/转化等 |
| 所需业务规则 | 商品运营规则、项目评分标准、类目规则（Store）；核心/可选维度划分可配置 |

| 依赖 | 健康分须基于结构化事实与可配置权重确定性计算，模型仅解释；不同商品对比时须考虑完整度，避免「全量数据商品」与「半量数据商品」直接误比；V1 无流量/转化时降级并标注完整度（数据设计标明是否用合成数据） |

### OP-08 销售异常诊断

| 字段 | 内容 |
|------|------|
| 角色 | 运营 |
| 优先级 | **P0** |
| 典型问题 | 「为什么这周销量突然下降？」 |
| 业务目标 | 在**可配置基线/阈值/历史对比**定义异常后，给出异常事实、可能原因 Top N、证据与建议 |
| Agent 步骤 | **按规则判定是否异常** → 查销量趋势 → 查库存/价格/退货/评价/反馈 →（若有）查流量/转化 → 归因排序 → 输出 |
| 所需业务事实 | 销售、库存、价格历史、退货、评价、反馈、活动；流量/转化可选 |
| 所需业务规则 | 异常基线与阈值（Store 可配置）；可选运营/活动规则 |
| 所需能力 | 查询销售/库存/价格历史/退货/反馈；销售异常分析（含异常判定） |
| 输出 | 是否异常及判定依据 + 异常事实 + 可能原因 Top 3 + 证据 + 建议 |
| 风险与审批 | 低；无需审批 |
| 依赖 | **异常不得由模型主观认定**；须先有可配置的基线/阈值/历史对比结论，再由模型解释可能原因。V1 无流量/转化时，归因限定在已有事实 |

### OP-09 价格分析与调价建议

| 字段 | 内容 |
|------|------|
| 角色 | 运营 |
| 优先级 | **P1** |
| 典型问题 | 「哪些适合降价？」 |

## 7. 客服 ↔ 运营业务闭环

本项目差异化主线之一：两角色不割裂。

正确关系是**共享反馈事实，分角色消费**，而非 CS-12 必须生产持久化结果再交给 OP-13：

```text
              底层反馈 / 评价 / 退货等事实
                         │
          ┌──────────────┴──────────────┐
          ↓                             ↓
   CS-12 客服视角汇总              OP-13 运营视角诊断
   （话术 / 个案理解）              （商品问题 / 经营归因）
          │                             │
          └──────────────┬──────────────┘
                         ↓
              健康度 / 风险 / 运营建议（如 OP-07）
                         ↓
              优化 / 调价 / 促销 / 补货建议
                         ↓
              商品 / 价格 / 库存等业务事实变化
                         ↓
              客服再查询当前事实 → 准确回复消费者
```

文档要求：演示与验收时应能讲清这条闭环，而不仅是孤立场景点选。
